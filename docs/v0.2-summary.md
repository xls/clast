# Clast v0.2 - what changed and why

Branch: `feature/v0.2-smart-index` (nothing pushed, `main` untouched).

## Short version

v0.1 was a tree-sitter symbol table with name-matched call edges behind 7 JSON tools. v0.2 is a rewrite
of the index and the tools around one question: how few round trips and tokens does an agent need to
find, read and understand code?

- **13 tools** (`clast_stats` for exact counts and inventories was added after the first write-up, together
  with the real-session A/B benchmark described in the README), compact text output, batched lookups, ranked search with typo / abbreviation / plain-word
  queries (also matched against what function bodies mention), exact symbol source read fresh from disk.
- **A call graph that knows types**: declared receiver types, import visibility, inheritance, call chains
  (`a.b().c()`), variables initialised from calls, import aliases and default exports, argument counts
  (overloads), `super` calls, Go packages, C# generic arity and partial classes. Name-only guesses are
  labelled instead of presented as facts.
- **New capabilities**: find references, type hierarchy (incl. Go structural interfaces and Ruby mixins),
  repo map, text search over all text files with the enclosing symbol on every hit, git change impact.
- **14 languages**: TypeScript, TSX, JavaScript, Python, Java, C#, Go, Rust, C, C++, Ruby, PHP, and new
  in this branch Swift and Dart.
- **Faster and safer**: native `node:sqlite` on disk instead of an in-memory sql.js database rewritten
  to disk after every file; parallel parsing; non-blocking server start; warm start in milliseconds to
  about 2 s; queries re-check the files they quote so results are never stale.
- **Verified**: 250 tests (unit per language, integration, precision regressions, end-to-end MCP session,
  watcher), eight rounds of evaluation by reviewer agents on 17 real repositories, and an A/B comparison
  against grep + read.

In the A/B runs (10 navigation questions per repo, identical for both arms, answers equivalent):

| Repo | Arm | Tool calls | Wall time | Tokens used by the agent |
|------|-----|-----------:|----------:|-------------------------:|
| django (Python, 3k files) | clast | 2 | 48 s | 59k |
| django | grep + read | 19 | 54 s | 68k |
| kafka (Java, 6.5k files) | clast | 2 | 41 s | 63k |
| kafka | grep + read | 21 | 99 s | 80k |
| vscode (TypeScript, 15.7k files) | clast | 3 | 68 s | 65k |
| vscode | grep + read | 15 | 60 s | 71k |
| rails (Ruby, 3.6k files) | clast | 2 | 52 s | 66k |
| rails | grep + read | 21 | 69 s | 77k |

(Token counts include each agent's fixed prompt overhead, so the relative saving on the navigation
itself is larger than the totals suggest. Four repos, one run each: indicative, not a benchmark suite.
The clast arm batched several CLI commands per shell call; through MCP each command is one tool call,
so expect roughly 10-17 calls there versus 15-21, but with far less output to read per call. The A/B
runs were done before evaluation rounds 4 to 8 described below, so they do not reflect the later
precision work.)

## What was wrong with v0.1

Found while reading the code before changing anything:

| Area | Problem |
|------|---------|
| Startup | The server indexed the whole repo before connecting the MCP transport. On a large repo the client times out ("Connection closed"). |
| Storage | sql.js keeps the database in memory and `db.save()` exported and rewrote the entire file after every parsed file: quadratic I/O. |
| Call graph | Edges were resolved by bare name with `LIMIT 1`: the first symbol with that name anywhere won. Re-resolved for all unresolved edges on every file change. Deleting a file left dangling callee ids. |
| Symbols | `parent_id` was never set, so "method" vs "function" and "parent class" were always wrong. C/C++ names came out as `foo(int a)`. Go types were classes. `.h` was always C. |
| Search | `LIKE '%q%'` with no ordering: no ranking, no fuzzy, no word match. |
| Bodies | Function bodies were stored truncated at 2000 chars, so the "context" tool could not show a whole function, and line numbers went stale between watcher events. |
| Freshness | Files deleted while the server was down stayed in the index forever. Only the root `.gitignore` was read, and only by the watcher; the initial scan ignored it. |
| Watcher | Looked up nodes by absolute path where the DB stores relative paths; skipped every dot-path. |
| Memory | Tree-sitter trees were never freed (WASM heap leak). Comment lookup split the whole source into lines for every symbol. |
| Output | Pretty-printed JSON: a large share of every response was braces, quotes and key names. |
| Hygiene | No tests. Four different version numbers (README 0.1e, package 0.1.2, server 0.1.0, plugin 0.1.0). Unused `@anthropic-ai/sdk` dependency. Wrong repository URL in the plugin manifest. VS Code extension pointed at a package name that does not exist. Generated LLM comments were deleted whenever their file was re-indexed. |

## Architecture

```
src/
  cli.ts              bin: MCP server (no args) or CLI commands mirroring every tool
  engine.ts           Clast = config + database + indexer for one project
  config/             zod-validated config, defaults
  db/index.ts         node:sqlite schema (v24), bulk-load mode, write path
  parser/
    spec.ts           LangSpec + Ctx API that language specs program against
    extractor.ts      one tree walk per file -> symbols, calls, imports, heritage, identifiers, type hints
    returns.ts        return type from a signature (for call chains)
    langs/*.ts        one spec per language (TS/TSX/JS, Python, Go, Rust, Java, C#, C/C++, Ruby, PHP, Swift, Dart)
  indexer/            scan (gitignore-aware), worker pool, import resolution, freshness checks
  query/              search ranking, call resolution, arity, call graph, hierarchy, formatting
  tools/              the 12 tools as functions returning text (shared by MCP server and CLI)
  server/index.ts     MCP registration, instructions, background indexing
  watcher/            chokidar, debounced, serialised
test/                 250 tests: per-language extraction, integration, chains/aliases, precision, watcher, MCP e2e
bench/                bench.mjs (speed), resolution.mjs (call-resolution rates)
```

What is stored per file: symbols (qualified name, kind, signature, doc, range, parent, exported, return
type), call records ("symbol A calls name N with K arguments on receiver R of declared type T,
optionally via call C"), imports with bound names and aliases, heritage (extends / implements / mixins,
with qualifier and generic arity), identifier occurrences (name -> lines, for find-references and
body search), declared field types, default export.

Key design decision: **call edges are resolved when queried, not when indexed.** v0.1 stored a callee id
per edge and had to re-resolve the world on every change. v0.2 stores what the source says and links at
query time with per-request caches, so an edit to one file can never leave another file's edges stale,
and resolution logic can use everything in the index.

## The tools

| Tool | Purpose | Notes |
|------|---------|-------|
| `clast_overview` | Repo / directory map | Languages, layout expanded where the code is (budgeted), most referenced symbols, hub files, entry points |
| `clast_file_summary` | File or directory outline | Signatures with line ranges and doc summaries, imports, importers; capped for huge files; Ruby visibility |
| `clast_search` | Ranked symbol search | Stages: exact, prefix, word abbreviation (`KProd`), initials (`gcn`), FTS over names/signatures/docs with stemming, function bodies that mention the query words, substring, fuzzy subsequence, edit-distance typos. | `clast_get_context` | One symbol, everything | Exact source from disk, doc comment capped so it cannot eat the budget, callers (resolved / name-only / unknown receiver / tests), callees, overloads, overrides, subtypes, methods defined outside the type body (Go receivers, Rust impls, C++ out-of-line); lists candidates when a bare name is ambiguous |
| `clast_call_graph` | Callers / callees tree | Depth N, hubs not expanded, `within` path filter, tests summarised by default, external names answered by call site; a bare name covers all overloads, `path:line` selects one (by argument count) |
| `clast_references` | All uses of an identifier | Lines with enclosing symbol; definitions do not eat the limit |
| `clast_hierarchy` | Super / subtypes, method families | Transitive; alias-aware; Go interfaces by method set (names plus parameter / result counts); Ruby mixins; C# partial classes merged |
| `clast_grep` | Text search | All text files (indexed first), enclosing symbol on each hit, literal fast path |
| `clast_changes` | Git diff -> symbols -> impact | Touched symbols, callers outside the change, tests that exercise them |
| `clast_status`, `clast_reindex`, `clast_comment` | Housekeeping | Comment generation kept from v0.1 (now survives re-indexing) |

Shared behaviour: plain text output; arrays for batching; symbols addressable as `name`,
`Class.method`, `path:name`, `path:line`, `pkg.module.name`, inherited members (`Engine.GET`, with a
note saying which type actually defines the member); every "not found" says what to try next; tool
list is about 3.4k tokens, server instructions about 400. While a first-time index is still being
built, query tools answer "building, N of M files, call again shortly" instead of a slow partial result.

### How a call gets resolved

In order of strength:

1. **Declared receiver type**: parameters, typed locals, fields (also across files: C++ headers, partial
   classes), constructor parameter properties, PHPDoc `@var` / `@param`, `x = Foo()` / `new Foo()`,
   and fields of a typed variable whose class lives in another file (`opts.logger.info()`).
2. **Call chains and call-initialised variables**: the receiver of `c` in `a.b().c()` is the declared
   return type of `b` (signature or `@return`), same for `x := load(); x.Run()`.
3. **this / self**: own class, then ancestors, then descendants (abstract hooks). **super / base /
   parent**: the inherited implementation, never the caller's own method.
4. **Imports**: a bare name must be defined in the file or imported into it (Python, JS/TS); a name
   imported from outside the project is external. Aliases (`import { X as Y }`, `use A as B`), renamed
   re-exports (`export { A as B } from`), default exports, `module.exports = require(...)`
   pass-throughs and Java static imports are followed. An imported module-level instance has the type
   it was created with (`pre_save = ModelSignal()` ... `pre_save.send()`).
5. **Static / namespace receivers**: `Foo.bar()`, `pkg.Func()`, `ns::func()`, Python submodules
   (`from pkg import text` ... `text.slugify()`).
6. **Evidence for untyped receivers**: receiver name vs class name (`repo` ~ `UserRepository`), same
   file, imports, file mentions the class, distinctive method name defined once. Common method names
   (`get`, `add`, `push`, ...) need receiver-name evidence, otherwise the site is reported as
   "receiver type unknown" rather than attributed to a guess.

Filters applied to every candidate:

- **Argument count** (Java, C#, Go, C, C++, TypeScript, Python, Rust): a call with 0 arguments is not a
  call of a 6-parameter method. Defaults, varargs, `self`, C# extension methods and `Emitter<void>.fire()`
  are understood. This is also what separates overloads.
- **Which type of that name**: Go `pkg.Type` is checked against the file's imports (an external
  `lazycache.Cache` or `io.Closer` is not the project's `Cache` / `Closer`); a class imported from one
  module, or defined in the same package / namespace, is not a same-named class elsewhere (TS, Python,
  Java, PHP, Dart); C# `Foo` is not `Foo<T>`; Ruby constants are looked up lexically; Rust
  `futures_io::AsyncRead` or a `Wake` imported from `std` is not the local trait; C `static` functions
  stay in their file.
- **A receiver name that fits two classes** (`user.set_password()` with `AbstractBaseUser` and
  `AnonymousUser`) never yields a certain edge.
- **Tests and vendored trees**: production code never resolves into tests or into vendored code it
  does not import.

Who counts as a caller of `X.m`:

- a call bound to `X.m` itself, or to a prototype twin; for a bare name also calls of its other
  overloads (address one overload as `path:line` to get only the calls whose argument count fits it);
- for a constructor, the sites that create the class with a fitting argument count;
- a call bound to the declaration of `m` on a supertype or interface of `X` (dynamic dispatch may
  reach `X.m`), unless the receiver is statically a sibling class or the call is `super.m()`;
- in Go, a call through an interface that `X` satisfies structurally, listed as possible ("?"), since
  any type with those methods satisfies it;
- not a call bound to an override of `m` in a subclass of `X`.

### Evaluation rounds

Reviewer agents used the CLI on real repos and verified answers against grep/read. Each round's
defects were fixed before the next; the "correct without help" figures are the reviewers' own counts
on deliberately hard questions and were not re-measured after the fixes.

- Round 1 (5 agents): about half of the tasks were answered correctly by the first call; the main defect
  class was name-only member calls reported as certain.
- Round 2 (4 agents) after the resolver rewrite: most round-1 defects fixed; remaining issues were
  chained calls, aliases, hierarchy across same-named classes, slow lookups for very common names.
- Round 3 (2 agents) after chain / alias / return-type work: 9 of 12 and 8 of 14 new tasks correct on
  the first call, none unanswerable in TS/JS/Python.
- Round 4 (2 agents: tokio + hugo, aspnetcore + laravel): 11 of 26 and 21 of 36. Found: external Go
  types matched by bare name, calls through embedded Go fields, `impl Trait for Arc<T>`, Go method
  sets without signatures, C# arity / partial / static classes, a C++ class listed as implementer of a
  C# interface, callers of a base method including calls bound to subclass overrides. All fixed.
- Round 5 (2 agents: django + kafka, vscode + redis): 13 of 26 and 17 of 25. Found: `super().m()`
  bound to the enclosing method, calls on sibling subclasses listed for an override, Java overloads
  conflated, same-named classes in different backends, C static functions merged across files,
  production `testing/` directories classified as tests. All fixed, each with a regression test in
  `test/precision.test.ts`.
- Round 6 (2 agents, the round-4 repositories again, new questions): tokio + hugo 20 of 31 (was 11 of
  26); aspnetcore + laravel 14 of 27 on questions aimed at overloads, namespaces and partial classes
  (was 21 of 36 on a broader set). Found: stdlib `io.Closer` / `std::task::Wake` taken for project
  types, Go embedded types losing their package, structural interface calls shown as certain, a bare
  name returning one overload's callers only, constructor callers missing, `$this->save()` in a trait
  reported as external, PHP classes with the same short name sharing callers. Fixed, with tests.
- Round 7 (2 agents, the round-5 repositories again, new questions): vscode + redis 26 of 34 (was 17
  of 25); django + kafka 16 of 24 (was 13 of 26). Found: Java static imports unresolved (175 files in
  kafka), calls on imported module-level instances dropped, `text.slugify()` through a submodule
  import, renamed re-exports invisible, `super.dispose()` ambiguous when the base class has a vendored
  copy, functions called only from C macro bodies looking unused. Fixed, with tests.
- Round 8 (2 agents, the languages least re-checked: rails + express + fastapi 40 of 51; leveldb +
  gin + ripgrep + Alamofire 46 of 60). Found: C++ namespace-level functions called from out-of-line
  methods reported as external (the largest recall bug of the whole exercise; leveldb's resolved rate
  went from 59% to 63% with the fix), Ruby calls written as a bare identifier (`save`) not recorded,
  Ruby `super` in mixins, a top-level Ruby class attached to a nested class of the same name, two Rust crates' `Error::kind` treated as one definition, a C#
  helper class nested in a test utility shadowing the real one (aspnetcore resolved rate 39% to 44%).
  Fixed, with tests; what remains is in the limitations below.

The Ruby bare-call change made at the very end was checked separately on rails: 0 wrong among about
70 certain edges inspected (parameters, block parameters and assigned locals of the same name were
all left out), 10 of 14 sampled bare calls found. The 4 misses were `loaded!` lookups, and the one
questionable edge it reported was a local variable named like its own method; both fixed since.

Precision of edges shown as certain (no "?"), audited on the final build by two more agents that read
the cited lines: vscode 1 wrong of 45, django 1 of 39, kafka 0 of 57, aspnetcore 1 of 58, so 3 wrong
of 199. Two of the three were fixed afterwards (a local array shadowing a field of the same name in
TypeScript; `string.IsNullOrEmpty` matched to a project helper of that name in C#); the third stays:
a local variable that holds a class (`ChangeList = self.get_changelist(...)` in Python).

A second audit of the same kind on the other languages, not acted on (it arrived at the end of the
session): tokio 0 wrong of 17, laravel 0 of 19, hugo 1 of 19 (`s.siteVector.Language()` attributed to
`Site.Language` instead of the field's type), rails 4 of 18. The four rails errors are one cause and
it is a real weakness: a bare `say` inside Thor generators was bound to `ActiveRecord::Migration#say`
because the generator classes inherit from a class called `Base` and the hierarchy is matched by
short name; the reviewer estimates most of that method's 36 "resolved" callers are wrong for the
same reason. Ruby classes with very common names (`Base`, `ClassMethods`) need qualified identity
before Ruby "certain" edges deserve the same trust as the typed languages.

Update after the write-up: that cause is fixed. Ruby classes and their ancestors are now compared by
qualified name with lexical constant lookup (`test/ruby-identity.test.ts`); on rails
`callers Migration.say` went from 36 "resolved" callers to 1 (the real one), the rest are shown as
name-only. Ruby has not been re-audited since. The hugo field-chain case is still open.

Across rounds 4 to 8 the share of first answers judged correct went from roughly 45-60% to 65-78%
on comparable repositories, with new and deliberately harder questions each time.

## Known limitations (honest list)

- **Untyped receivers** in dynamic code (`obj.save()` in Python, callbacks in JS) cannot be attributed.
  They are reported separately as "receiver type unknown" instead of being guessed or dropped.
- **Types are matched by name plus the checks listed above.** Two classes with the same short name in
  PHP namespaces or Java packages can still be confused when nothing in the calling file tells them
  apart, most visibly for untyped receivers and container results (`$this->make(Kernel::class)->handle()`).
- **C#**: generic method overloads that differ only in type arguments (`UseMiddleware<T>(args)` vs
  `UseMiddleware(Type, args)`) are one target; target-typed `new(...)` is not attributed; base classes
  declared in `.razor` files are not seen.
- **Rust**: `impl Trait for Arc<T>` is recorded only when `T` is defined in the same file; `if let
  Some(x) = call()` does not type `x`; blanket impls are not listed as implementers.
- **Ruby**: a bare identifier inside a method (`save` with no receiver, arguments or parentheses)
  is recorded as a call unless the method binds a local of that name; bare names that are neither
  (attribute readers defined by metaprogramming) end up in the "external" list. `prepend` /
  `include` inside `on_load` blocks is not attached to the target class. Modules all called
  `ClassMethods` are told apart only by their enclosing namespace.
- **Swift**: the tree-sitter Swift grammar fails on some files depending on what was parsed before
  them (Alamofire's `DataStreamRequest.swift`: the members are indexed, the enclosing class is not).
  Overloads that differ only in argument labels are one target.
- **C++**: `db->rep->Get()` through a chain of pointer fields is not typed; classes declared inside a
  function body are not listed as subtypes.
- **Generics and inference**: `Plugin<Partitioner>.get().partition()` is not followed (no generic
  substitution). TypeScript inferred return types are unknown unless annotated.
- **Overloads that differ only in parameter types** (same count) are still one target
  (`poll(Duration)` vs `poll(Timer)`).
- **Framework conventions** are not modelled: Django `Model.objects.get_or_create()`, Laravel facades
  and container lookups, dependency-injected services resolved by string or class constant.
- **Rust**: an inherent method and a trait method of the same name on one type share callers.
- **Metaprogramming**: Rails `define_method`, dynamic dispatch through strings, macros that generate
  items (partly recovered for Rust `macro_rules!` wrappers) are invisible; the tools point to grep.
- **Search is lexical**: names, signatures, docs and identifiers used in bodies, with stemming. A
  description that shares no word with the code ("where are aliases written to disk" when the code
  says `publishDestAlias`) finds the neighbourhood, not always the function.
- **Very common names** on huge repos: `callers IDisposable.dispose` on vscode takes 5-6 s and says
  how many sites were examined; scoped with `within` it is complete and fast.
- **Property / field references** are matched by name (`->flags` on any struct); they are listed as
  "referenced without a call", not as resolved callers.
- **Go**: cross-file `var _ I = (*T)(nil)` assertions are not recorded; the module path is inferred
  from the imports (no go.mod parsing).
- **Swift / Dart** specs are new and less exercised than the others (11 tests each, tried on Alamofire
  and dart-lang/http).
- **Not indexed**: Kotlin, Scala and others (no grammar in the bundle). `clast_grep` still searches
  those files as text.
- **CLI**: every query command first rescans the tree for changes (1.5-2 s on 10k+ files); pass
  `--no-scan` when running several commands in a row. The MCP server does not have this cost.
- **Index size**: about 12-25 MB per 1,000 source files (vscode: about 360 MB).
- Cold index of very large repos is bounded by single-threaded SQLite writes (vscode: about 27 s).
